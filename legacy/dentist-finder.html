Dentist Finder

A self-initiated product exploring a clearer way to search for and compare dental practices, taken from concept to a functional online version with its own design system.

Context and challenge

Finding a dental practice online often means scrolling through inconsistent listings with little useful information to compare. Dentist Finder started as a personal initiative to explore a clearer, more structured way to search for and compare dental practices.

The challenge was less about any single screen and more about consistency: every practice needed to be searchable, filterable and comparable through the same structure, and the interface needed a system that could grow without breaking that consistency.

My role and collaboration

I was responsible for the product concept, information architecture, user flows, wireframes, UX/UI design and the responsive interface, working with one software developer on technical implementation.

Because it was a two-person project, I also designed the underlying design system myself: the visual foundations, tokens and components that kept the interface consistent as new screens were added.

Approach

  1. Defined the core user task — searching for and comparing dental practices — and mapped it into a simple flow from search to profile.

  2. Sketched low-fidelity wireframes for the key screens before any visual design, to test the structure of search, filtering and comparison.

  3. Built a design system of reusable components and tokens so new screens and states could be added consistently.

  4. Worked with a developer to bring the flow to a functional online version.

Key design decisions

Search and filter before individual profiles

Patients needed to narrow down options before committing to reading a full profile, so filtering came first in the structure rather than being an afterthought.

A shared card and profile format for every practice

Comparable information mattered more than distinctive layouts, so every practice used the same structure for its core details, regardless of size or specialty.

A token-based design system from early on

With only two people building the product, consistency had to come from the system itself, not from manually checking every new screen against the last one.

Design system

As a two-person team, the design system did the work a larger team would normally split across several people. It kept new screens consistent and made the product easier to extend as the scope grew.

Foundations

Colour, typography, spacing and grid rules defined once and reused across every screen, so new work started from the same base.

Colour and typography tokens

Core colours and type styles were set as tokens rather than one-off values, so a change in one place updated the whole interface consistently.

Mint Ink Yellow Surface

Spacing and layout rules

A consistent spacing scale and grid kept search results, cards and forms aligned across the platform instead of being adjusted screen by screen.

Reusable components

Search fields, filters, cards, buttons, navigation and form fields were built once as components with defined variants, then reused across the product.

Interface states

Each interactive component had defined default, hover, focus, selected, error and disabled states, so behaviour stayed predictable wherever a component appeared.

  • Default
  • Hover
  • Focus
  • Selected
  • Error
  • Disabled

Responsive behaviour

Components were designed to adapt across desktop, tablet and mobile layouts using the same underlying structure, not separate designs per breakpoint.

The solution

The core journey runs from search to profile: a patient enters a location or need, narrows the results with filters, then compares practices through a shared card format before opening a full profile for details.

Outcome

Dentist Finder reached a functional online version where users could search for and compare dental practices through the interface and design system built for it. As a two-person project, the system itself — not a large team — kept the product consistent as it grew.

Reflection

Building both the product and its design system with one developer meant every shortcut would have shown up later. Keeping the token and component structure disciplined from the start made new screens faster to design, and it's the part of this project I'd carry into any small-team product.
